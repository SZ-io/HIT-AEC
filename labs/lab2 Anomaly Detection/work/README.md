# Lab 2 — Anomaly Detection: Stolen Account (realistic synthetic logins)

Main notebook: `work/AnomalyDetectionComparison.ipynb`

## 1. Overview and scenario

The account of a normal user (**User**) is stolen and used by an attacker. The goal is to find the attacker's logins with two anomaly-detection models and compare them.

- **MITRE ATT&CK T1078 — Valid Accounts:** the attacker logs in with User's real password.
- **MITRE ATT&CK T1110 — Brute Force:** some logins come after a few failed password guesses.

In this project the attacker logs in **from Israel**, and **every value he can produce can also be produced by User**. Both are generated by the same function, from the same lists. Only the **probabilities** are a little different. No single value proves an attack, so the models must find unusual *combinations* and *frequencies*, just like in a real SOC.

| | count | share |
|---|---:|---:|
| Normal logins | 1000 | 96.15% |
| Attack logins | 40 | 3.85% |

## 2. Data generation

All data is synthetic. Every value is a random draw from a **probability distribution** (normal, Poisson, gamma, Bernoulli, weighted choice) with NumPy `default_rng` (seeds 50 and 42), and realistic dates and IP addresses come from the **Faker** library (`Faker.seed(50)`). The data is *pseudo-random*: random-looking, but the same in every run, so the results can be reproduced.

### Columns

| column | type | used by models | description |
|---|---|:-:|---|
| `timestamp` | datetime | no | Faker date (May-Oct 2026) + login hour and minute |
| `hour` | numeric | yes | login hour (0-23) |
| `is_weekend` | numeric (0/1) | yes | Friday or Saturday (Israeli weekend) |
| `distance_km` | numeric | yes | distance from User's home in Tel Aviv |
| `failed_attempts` | numeric | yes | failed attempts before the successful login |
| `country` | categorical | yes | IL (or GR / CY on a business trip) |
| `city` | categorical | yes | one of 12 Israeli cities |
| `device` | categorical | yes | MacBook, iPhone, Windows, Android |
| `browser` | categorical | yes | Safari, Chrome, Firefox, Edge |
| `isp` | categorical | yes | Bezeq, HOT, Partner, Cellcom, Pelephone, Golan Telecom |
| `ip_address` | string | no | Faker IP inside an Israeli-like range of the ISP (for the analyst only) |
| `is_attack` | label | no | 0 = normal, 1 = attack (only for evaluation) |

### One generator, two profiles

A single function, `generate_logins(n, profile)`, creates the logins for **both** User and the attacker. A *profile* is a dictionary of probabilities:

| column | how it is generated |
|---|---|
| `hour` | Normal(mean, std), rounded, clipped to 0-23 |
| `is_weekend` | Bernoulli(`p_weekend`) |
| `timestamp` | Faker date that matches `is_weekend`, + the hour and a random minute |
| `city` | weighted choice from the 12 cities |
| `distance_km` | haversine distance between real city coordinates and User's home + Gamma(2, 1.5) noise (geo-IP error) |
| `failed_attempts` | Poisson(`failed_mean`) |
| `device` | weighted choice |
| `browser` | weighted choice that depends on the device (Safari only on Apple devices) |
| `isp` | with probability `p_usual_isp`, the ISP User normally has in that place (office in Ramat Gan = Partner, home in Tel Aviv = Bezeq, Herzliya = HOT, phone = Cellcom); otherwise a weighted random ISP |
| `ip_address` | with probability `p_known_ip`, one of User's known IPs; otherwise a new Faker address in the ISP's range (e.g. Bezeq 79.176.x.x, Partner 85.64.x.x, Cellcom 77.124.x.x) |

### User vs. attacker probabilities

User lives in Tel Aviv and works in Ramat Gan.

| parameter | User (normal) | Attacker |
|---|---|---|
| `hour` | Normal(12.5, 2) | Normal(15, 4) |
| `p_weekend` | 5% | 25% |
| `city` | Ramat Gan 50%, Tel Aviv 33%, Herzliya 7%, other 9 cities 10% | spread over all 12 cities (Tel Aviv 20%, Ramat Gan 12%, Jerusalem 10%, ...) |
| `failed_attempts` | Poisson(0.3) | Poisson(1.3) |
| `device` | MacBook 78%, iPhone 17%, Windows 3%, Android 2% | MacBook 40%, iPhone 15%, Windows 30%, Android 15% |
| `browser` (Apple) | Safari 62%, Chrome 33%, Firefox 3%, Edge 2% | Safari 35%, Chrome 45%, Firefox 12%, Edge 8% |
| `browser` (other) | Chrome 80%, Firefox 10%, Edge 10% | Chrome 60%, Firefox 20%, Edge 20% |
| `p_usual_isp` | 85% | 15% (only by chance) |
| random `isp` | Pelephone 5%, Golan 5%, others 90% | Pelephone 20%, Golan 25%, others 55% |
| `p_known_ip` | 90% | 0% (always a new IP) |

### Step 3 — making the data harder

**Legitimate exceptions of User (7% of normal rows).** Each one changes only one or two features, so it looks a little suspicious but is benign:

| scenario | rows | change |
|---|---:|---|
| `late_work` | 20 | `hour` 19-22 |
| `trip_in_israel` | 20 | Jerusalem / Haifa / Be'er Sheva, `isp` = Cellcom |
| `forgot_password` | 20 | 3-5 `failed_attempts` |
| `business_trip` | 10 | GR or CY, 500-2000 km, MacBook + Safari, working hours |

**Mimic attacks (10 of the 40 attacks):** the attacker copies User's habits: MacBook, Safari or Chrome, working hours on a weekday, Tel Aviv or Ramat Gan, 0-1 failed attempts. Only the ISP and the new IP may still be different, and sometimes even the ISP is one User uses.

After every change, `timestamp` and `ip_address` are generated again, and two checks (`assert`) confirm that the timestamp's hour equals `hour` and its weekday matches `is_weekend`.

The `scenario` column is kept outside the data and used only to explain the results. The models never see it.

## 3. Models

### Data split
60% train / 20% validation / 20% test, **stratified** by `is_attack`. The test set has 208 rows: 200 normal and 8 attacks.

### Model A — Isolation Forest
- One-hot encoding of the categorical columns + `StandardScaler` for the numeric columns (fitted on train only).
- `n_estimators=300`, `contamination` = share of attacks in train (3.85%).
- Score = `-decision_function` (higher = more anomalous); a score above 0 means the row is flagged.

### Model B — Autoencoder with categorical embeddings (Keras, torch backend)
- Numeric inputs are scaled; each categorical column becomes an integer id (0 = unknown) and goes through a trainable **embedding** layer.
- Encoder: Dense(32) → **latent Dense(8)** (the behavioural embedding) → decoder Dense(32) → outputs.
- Outputs: numeric reconstruction (MSE) + one softmax per categorical column (cross-entropy, weight 0.35).
- Trained **only on normal train rows**, with early stopping on normal validation rows.
- Anomaly score = numeric MSE + 0.35 × mean categorical negative log-likelihood.
- Threshold = **99th percentile** of the scores of normal validation rows (0.848).

## 4. Results (test set: 208 rows, 8 attacks)

### The four possible outcomes

| | model says **attack** | model says **normal** |
|---|---|---|
| **really an attack** | **TP** — true positive (caught) | **FN** — false negative (missed attack) |
| **really normal** | **FP** — false positive (false alarm) | **TN** — true negative (correctly ignored) |

### Confusion matrices

| | TP | FN | FP | TN |
|---|---:|---:|---:|---:|
| **Isolation Forest** | 5 | 3 | 7 | 193 |
| **Autoencoder** | 5 | 3 | 5 | 195 |

### Metrics

| metric | formula | Isolation Forest | Autoencoder | meaning |
|---|---|---:|---:|---|
| Detected anomalies | TP + FP | 12 | 10 | how many alerts the analyst gets |
| **Precision** | TP / (TP+FP) | 5/12 = **0.42** | 5/10 = **0.50** | of the alerts, how many are real attacks |
| **Recall** | TP / (TP+FN) | 5/8 = **0.62** | 5/8 = **0.62** | of the real attacks, how many were caught |
| **F1** | 2·P·R / (P+R) | **0.50** | **0.56** | one number that balances precision and recall |
| False positive rate | FP / (FP+TN) | 7/200 = 3.5% | 5/200 = 2.5% | how often a normal login raises a false alarm |
| Accuracy | (TP+TN) / all | 95.2% | 96.2% | misleading here (see below) |

**Why accuracy is not useful here:** a "model" that never raises an alert gets 200/208 = **96.15%** accuracy and catches zero attacks. With only about 4% attacks, precision, recall and F1 are the measures that matter.

### Agreement between the models

- Agreement rate: **98.08%** (204 of 208 rows get the same label).
- Flagged by both: **9** (5 attacks + 4 false alarms).
- Only Isolation Forest: **3** (all normal: rows 96 and 911 are business trips, row 891 is a normal login on iPhone + Edge + Golan Telecom).
- Only Autoencoder: **1** (row 515, a normal login with Pelephone on a weekend).

### What each model flagged, by scenario

| scenario in test | rows | flagged by IF | flagged by AE |
|---|---:|---:|---:|
| attack | 7 | 5 ✅ | 5 ✅ |
| mimic_attack | 1 | 0 ❌ | 0 ❌ |
| business_trip | 4 | 4 ⚠️ | 2 ⚠️ |
| normal | 184 | 3 ⚠️ | 3 ⚠️ |
| late_work / forgot_password / trip_in_israel | 12 | 0 | 0 |

### What this tells us

- **Both models caught the same 5 attacks and missed the same 3.** All 4 disagreements are normal logins, so the models differ only in their **false alarms**, not in which attacks they find.
- **The 3 missed attacks:** the **mimic attack** (same MacBook, hours and city as User — it really looks normal, so missing it is expected), and two regular attacks that happened to draw normal-looking values (0-1 signals).
- **The autoencoder is a little better because it raises fewer false alarms (5 vs 7).** Isolation Forest flagged all 4 business trips, because 1,000+ km is a huge numeric outlier. The autoencoder flagged only 2, because it learned from the trips in training that "abroad + MacBook + Safari in working hours" can be normal behaviour for User.
- **The legitimate exceptions were handled well:** neither model flagged late work, a forgotten password or a trip inside Israel — exactly the logins that are only "a little bit odd".
- **Compared with the old data:** with attack-only values (PK, Linux, Golan, Android) the autoencoder had F1 0.88 and Isolation Forest 0.00 — the autoencoder was mostly detecting "a value I have never seen". Now the two models are close (0.56 vs 0.50), which shows that neither has a shortcut anymore.

### Limitations

- **Small test set: only 8 attacks.** One attack changes recall by 12.5 points; with another seed the recall could easily be 0.50 or 0.75. Running several seeds and reporting the average would give more stable numbers.
- **The autoencoder's threshold does not carry over exactly.** It is the 99th percentile of normal validation scores, so about 1% false alarms are expected, but on test it was 2.5% — normal behaviour has variance.
- **Precision of 0.42-0.50 is actually decent for a SOC:** about 1 real attack per 2 alerts. Real login-anomaly systems often have many more false alarms per real attack. Every alert still needs an analyst to check the context (travel calendar, new device, IP reputation).

### Conclusion

On this dataset and with these settings, the **autoencoder with embeddings** is slightly better: F1 0.56 vs 0.50, precision 0.50 vs 0.42, and 5 vs 7 false positives, with the same recall (0.62). Both models miss the attacker who copies User's habits, and business trips are the main source of false alarms. Because the models catch the same attacks but make different mistakes, a SOC analyst should treat alerts from both models as the strongest candidates and use human context to decide on the rest.

> AI detects patterns. Humans validate context and make the operational decision.
